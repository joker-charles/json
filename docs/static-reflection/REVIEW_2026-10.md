## 1. 已修复

### R1 容器 from_json 不校验 JSON 类型（高，静默错值）

`deserialize_one_impl` 的 array-like 分支直接 `for (auto&& e : j)`，object-like
分支直接 `for (const auto& item : j.items())`，**没有**上游
`detail::from_json` 数组/对象重载的 `is_array()` / `is_object()` 守卫。后果不是
抛异常，而是**静默接受**：

| 输入 → 目标 | 上游 | 修复前 refl2 |
|---|---|---|
| `json(5)` → `vector<int>` | `type_error.302` | `[5]` |
| `json("x")` → `vector<string>` | `type_error.302` | `["x"]` |
| `json(nullptr)` → `vector<int>` | `type_error.302` | `[]` |
| `json({"a":1})` → `vector<int>` | `type_error.302` | `[1]` |
| `json(5)` → `map<string,int>` | `type_error.302` | `{"":5}` |
| `json(5)` → `set<int>` | `type_error.302` | `{5}` |
| `json(5)` → `array<int,3>` | `type_error.302` | **`type_error.304`**（错误码也不对） |

根因是上游迭代器的两个“良性”特性：primitive 的 `begin() != end()`（恰好迭代
**一个**元素），以及 `items()` 对非对象返回**空键**而不是抛异常。`json(5)` 被
迭代成它自己，于是“数字 → `[5]`”。

差分矩阵（11 输入 × 10 类型 = 110 组）修复前 **30 组不一致**，修复后 **0 组**。

**修复**：在 array-like 分支补
`if (!j.is_array()) JSON_THROW(type_error::create(302, concat("type must be array, but is ", j.type_name()), &j));`，
在 object-like 分支补同形的 `is_object()` 守卫（与上游
`from_json_array_impl` / 对象重载的错误码、错误文本逐字一致）。固定尺寸分支
（`std::array`）由同一个守卫覆盖，`304` 一并回到 `302`。

### R2 固定尺寸容器错误码漂移（中，随 R1 修复）

`std::array<T,N>` 收到非数组时走 `j.at(i)`，在 `type_error.304`
（`cannot use at() with number`）处失败；上游在进入元素赋值前就抛 `302`。
R1 的守卫使错误码、消息与上游一致；短数组仍抛 `out_of_range.401`、长数组仍忽略
多余元素（与 `detail::from_json_array_impl<std::array<T,N>>` 一致）。

### R3 迭代/对象分支的同一守卫覆盖 insert 型容器（中）

`std::set` / `std::multiset` / `unordered_set` 的 insert 分支与顺序容器共用 array
守卫；修复前 `json(7).get<set<int>>()` 得到 `{7}`，现在 `302`。

### R4 HEAD 上的 `probe_coverage_boundary.cpp` 无法编译（测试损坏）

`probe_coverage_boundary.cpp` 末尾的 M7 往返走 `j.get<V>()`，而顶层
`std::variant` 支持自 2026-08 起由 `JSON_USE_REFLECTION_VARIANT` 单独门控；该
fixture 只定义了 `JSON_USE_REFLECTION`，因此 **HEAD 上该 TU 编译失败**
（`no type named 'type' in enable_if<false,int>`）。工作区已带修复（补 gate 与
说明注释），本次一并提交。

## 3. 未改的边界与待办

| # | 项 | 说明 | 建议 |
|---|---|---|---|
| B1 | 容器反序列化的**异常保证**与上游不同 | 上游 `from_json_array_impl` 先建临时容器、成功后 `arr = std::move(ret)`；refl2 `clear()` 后原地填充，元素失败时目标已被清空/部分填充（实测：`[1,"x",3]` 失败后 vector 上游保持 2 个旧元素，refl2 只剩 `[1]`） | 低危；若要逐字对齐，顺序/insert 分支改为「临时 + move 赋值」 |
| B2 | 注解模板特化 over 库类型不可序列化 | `in_json_namespace` 递归检查模板实参：`Box<int>` 可序列化，`Box<json>` 静默不参与 catch-all（换回“conversion from Box<json>”的模糊错误） | 文档化防御的已知代价；若要让 `Box<json>` 可用，需要不重入 catch-all 的 ADL 探针 |
| B3 | `map<非字符串键,T>` 的对象形式与上游不互操作 | 对象形式 `{"1":2}` 是 `VERIFIED_FACTS.md` 已记录的偏差；补充事实：上游 `get<map<int,int>>` **读不了**该形式（`302`），refl2 也读不了上游的 `[[1,2]]` 形式 | 已在既有文档记录方向；建议在 M5 文档补一句 wire 不互操作的后果 |
| B4 | 2026-08 的 O1–O6 仍未关闭 | BSON 长度 `int32` 截断、UBJSON 码表 `'d'` 未接线、读取器守卫、递归深度、>4 GiB 长度阶梯 | 见 `REVIEW_2026-08.md §4` |

> 说明：空结构体 / 全私有结构体在反射下仍不可序列化，这是
> `M5_REFLECTION_TO_JSON.md §3` 的**有意行为**（与宏一致：对空结构体
> `NLOHMANN_DEFINE_TYPE_*` 同样编译失败），不计为缺陷。
